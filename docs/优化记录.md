## P0-1　`AgentCache`：把"无界缓存"改成"有界缓存"

### 1.1 怎么发现的（现象）

排查"值得优化的点"时读到 `service/agent/AgentCache.java`：

```java
/** 缓存键 → Agent 实例。 */
private final Map<Key, Object> cache = new ConcurrentHashMap<>();   // ← 无上限、无过期
```

它**只增不减**：只有"改配置 / 删会话"时才会调用 `evictByConversation` / `clear`，
否则缓存条目会随「会话数 × 模型/技能/知识库等配置组合」一直累积。

### 1.2 根因与危害

- 每个缓存值是一个 **`ReactAgent`**，它持有 **一个 `ChatModel`** 和 **编译好的执行图**，单个对象就不小。
- 用户长期使用（开很多会话、来回切模型）后，**内存只涨不落** → 有内存泄漏风险，
  极端情况 OOM。
- 这是"**没写错，但设计不够**"的典型问题：功能正确，但缺少容量纪律。

### 1.3 方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 保持 `ConcurrentHashMap`，加个"满了就 clear" | 最简单 | 粗暴、会误伤热点；仍需自己写 | ✗ |
| B. 手写 LRU（`LinkedHashMap(accessOrder=true)` + `removeEldestEntry` + 同步） | 零依赖；**面试爱考** | 要自己处理并发、统计、过期，易出错 | 备选 |
| C. **Caffeine**（`maximumSize` + `expireAfterAccess`） | 工业级、Spring 生态标配、线程安全、一行配置 | 多一个依赖 | ✅ 采用 |

> Caffeine 由 **Spring Boot 的 BOM 统一管理版本**（`spring-boot-dependencies` 里有 `caffeine.version`），
> 因此 pom 里**不用写 version**（写死反而容易和 Boot 版本不一致）。

### 1.4 关键改动

```java
/** 缓存条目上限，超出后按「最近最少使用」淘汰。 */
private static final long MAX_ENTRIES = 64;
/** 空闲多久没被访问就淘汰。 */
private static final Duration EXPIRE_AFTER_ACCESS = Duration.ofMinutes(30);

private final Cache<Key, Object> cache = Caffeine.newBuilder()
        .maximumSize(MAX_ENTRIES)
        .expireAfterAccess(EXPIRE_AFTER_ACCESS)
        .build();
```

对外 API **完全不变**（`get` / `put` / `evictByConversation` / `clear` / `size`），
所以调用方（`AgentFactory`、`SessionService`）**一行都不用改**：

| 原来 | 现在 |
|---|---|
| `cache.get(key)` | `cache.getIfPresent(key)` |
| `cache.put(key, v)` | `cache.put(key, v)` |
| `cache.keySet().removeIf(...)` | `cache.asMap().keySet().removeIf(...)` |
| `cache.clear()` | `cache.invalidateAll()` |
| `cache.size()` | `cache.estimatedSize()`（**估算值**） |

> 细节：`evictByConversation` 的返回值原先用 `size()` 前后差算"清掉几条"。
> 换成 Caffeine 后 `estimatedSize()` 是**估算值**（可能滞后于内部维护），做差可能得到 0、日志会误导。
> 所以改成**先精确统计匹配键的数量，再删除**。

### 1.5 ★ 为什么"淘汰"是安全的（本项最重要的论证）

有人会问："把缓存淘汰了，用户聊到一半的上下文不就丢了吗？" **不会。** 原因是**职责分离**：

- `AgentCache` 缓存的是 **Agent（大脑 + 工具 + 图）**，它**不持有对话历史**；
- 对话历史在**全局共享的** `MysqlSaver`（MySQL 表 `graph_thread` / `graph_checkpoint`）里，按 `thread_id = 会话 id` 隔离（见 `AgentFactory` 注释）。

所以从缓存里淘汰一个 Agent，**最多是"下次访问时重建一次"**（多花一点构建开销），
**对话数据一条都不会丢**。这也是为什么可以放心设一个"不大"的上限（64）。

### 1.6 怎么验证

- `mvn clean test` → **84 个用例全绿**（`AgentCache` 的 API 未变，无回归）。
- 因为 Agent 相关 Bean 标注了 `@Profile("!test")`，契约测试**不覆盖**它；
  其行为由"结构（有界）+ 编译 + API 不变"保证，端到端由联调覆盖。

### 1.7 面试问答

**Q1：你怎么想到要优化缓存？**
> "我在做代码走查时注意到把一个 `ConcurrentHashMap` 当缓存用，且**没有任何容量或过期策略**。它只在删会话/改配置时清理，所以是'只增不减'的。缓存的值是一个 `ReactAgent`，内部持有模型和编译后的图，长期运行会持续占内存——这就是典型的**无界缓存导致的内存泄漏**，于是我把它换成了有上界的缓存。"

**Q2：为什么用 Caffeine，不自己写个 LRU？**
> "手写 LRU（`LinkedHashMap` + `removeEldestEntry`）确实能解决容量问题，面试也常考；但生产代码里我更倾向 **Caffeine**：它是 Spring 生态事实标准，线程安全、支持 `maximumSize` / `expireAfterAccess` / 命中率统计，而且**版本由 Spring Boot BOM 统一管理**，不会和框架打架。**自己写会引入并发正确性的风险，收益也不高。**"

**Q3：淘汰缓存会不会把用户的对话弄丢？**
> "不会。因为 Agent **不持有对话历史**——历史在共享的 `MysqlSaver` 里按 `thread_id`（会话 id）隔离。淘汰只是'下次重建一次 Agent'，**只损失一点重建开销，不丢任何数据**。这一点在设计缓存容量时很关键：**必须先确认'缓存里的东西是可重建的'，才敢设上限。**"

**Q4：`maximumSize` 和 `expireAfterAccess` 为什么取这两个值？**
> "`maximumSize=64`：条目数约等于'同时活跃的 (会话 × 模型 × 技能集…) 组合数'，个人助理场景远达不到，但能兜住极端情况。`expireAfterAccess=30 分钟`：远大于一次对话中的思考间隔（**不会聊到一半把 Agent 淘汰掉**），又能让偶尔用一次的会话及时释放。"

**Q5：如果业务改成"必须保证同一会话的 Agent 不被淘汰"怎么办？**
> "可以按 `conversationId` 做**权重/固定驻留**（Caffeine 支持 `weigher` 与 `pin` 思路），或对最近活跃的会话做保护；但那就需要重新评估内存预算了。"

## P0-2　补齐 PDF 正文抽取（让 PDF 能进 RAG）

### 2.1 怎么发现的（现象）

`FileService.extractText(...)` 里 PDF 分支是一个 TODO：

```java
if (PDF_EXTS.contains(ext)) {
    // TODO: 离线构建无法引入 Apache PDFBox。接入后在此调用 …
    // 当前返回空串（视为"扫描版 PDF 没抽到文本"），不进索引。
    return "";
}
```

后果：**用户上传 PDF → 抽不到正文 → 不进 RAG 索引 → 提问时检索不到 PDF 内容**。这是功能性缺口。

> 顺带纠正一条**过时的历史结论**：代码注释写的是"离线构建无法引入 PDFBox"，
> 但实测**本机 Maven 可以正常联网拉取**（`repo.maven.apache.org` 可访问），PDFBox 3.0.3 及其依赖均已成功下载。
> 所以这个"不能做"的前提已经不成立了。

### 2.2 方案与实现

用 **Apache PDFBox 3.x**（PDF 文本抽取的 Java 事实标准）。新增方法：

```java
private String extractPdf(byte[] data) {
    try (PDDocument doc = Loader.loadPDF(data)) {          // ← 3.x 的新 API
        String text = new PDFTextStripper().getText(doc);
        return text == null ? "" : text.trim();
    } catch (Exception e) {
        log.warn("PDF 正文抽取失败（不影响上传，仅不入索引）：{}", e.getMessage());
        return "";
    }
}
```

### 2.3 踩坑：PDFBox 3.x 的 API 变了

| 版本 | 加载方式 |
|---|---|
| PDFBox 2.x | `PDDocument.load(...)` |
| **PDFBox 3.x** | **`Loader.loadPDF(...)`**（静态方法；旧的 `PDDocument.load` 已**移除**） |

> 照抄网上 2.x 的示例会**编译不过**——这是升级依赖时最容易中的一枪。

### 2.4 依赖治理（这里有两个"干净度"细节）

```xml
<dependency>
    <groupId>org.apache.pdfbox</groupId>
    <artifactId>pdfbox</artifactId>
    <version>3.0.3</version>
    <exclusions>
        <exclusion>
            <groupId>commons-logging</groupId>
            <artifactId>commons-logging</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

1. **排除 `commons-logging`**：Spring Boot 已内置 **`spring-jcl`**，它提供了**同一套**
   `org.apache.commons.logging` API。若再把 `commons-logging` 拉进来，同一个包会出现两份实现（**经典类路径重复**）。
2. **确认过 PDFBox 的 `log4j-core` / `log4j-jcl` 是 `test` 作用域** → **不会**进运行时类路径 →
   Spring Boot 的日志实现**不会**被从 Logback 切换成 Log4j2（这是加第三方库时最容易忽略的副作用）。

### 2.5 降级策略（为什么要吞异常）

- **抽正文失败绝不能让"上传"失败**：宁可这个文件没进索引，也不能让用户传不上文件。
- **扫描版 PDF**（内容其实是图片）本来就抽不出文字 → 返回空串，上层据此"不入库"，
  在 `reindex` 时还会给出"**可能是扫描版 PDF 或空文件**"的提示。
- 与上传整体策略一致：**上传即索引失败只记日志，不影响上传**。

### 2.6 怎么验证（运行时探针，而不只是"编译通过"）

写了一个一次性探针：**用 PDFBox 现场生成一个带文字的 PDF，再用与 `extractPdf` 完全相同的 API 抽回**：

```
GENERATED_PDF_BYTES=771
EXTRACTED=[Hello IPAS PDF extraction 12345]
MATCH=true
```

→ 证明"造 PDF → 抽文字"这条链路在**运行时真的可用**（不只是能编译）。
（日志里那批 `FileSystemFontProvider / TTFParser` 的 WARN 是 PDFBox **首次扫描系统字体目录建缓存**时产生的，与抽取逻辑无关。）

### 2.7 面试问答

**Q1：你怎么发现 PDF 抽不通的？**
> "走查上传链路时，看到 `FileService.extractText` 里 PDF 分支是 `return ""` 加一个 TODO，注释说'离线装不了 PDFBox'。我实测发现本机 **Maven 能正常联网**，那条前提已经过时了，于是把它补上：**上传的 PDF 现在能抽正文并进 RAG 索引**。"

**Q2：为什么选 PDFBox？**
> "PDF 是复杂格式（压缩流、字符编码、CMap、嵌入字体），**不可能自己手写解析**。PDFBox 是 Apache 出品、Java 里最成熟的 PDF 处理库，抽文本只要两三行。**关键是要认清'什么该自己写、什么该用库'。**"

**Q3：加这个依赖你注意了什么？**
> "两点：① 排除了 `commons-logging`，因为 Spring Boot 的 `spring-jcl` 已经提供同一套 API，不排除会**类路径重复**；② 加了依赖后我确认了 PDFBox 的 `log4j-core` 是 **test 作用域**，不会污染运行时日志实现——**否则 Spring Boot 会从 Logback 切到 Log4j2**，日志配置就全变了。"

**Q4：抽不到文字怎么办？**
> "分层降级：**抽取失败抛异常 → 捕获后返回空串并记日志**，绝不影响上传；**扫描版 PDF 本来就抽不出文字** → 也不入库，并在重建索引时给用户'可能是扫描版 PDF'的明确提示。**核心原则是：辅助能力（抽文本）失败，不能拖垮主流程（上传）。**"

**Q5：这个改动怎么验证的？**
> "两步：先 `mvn clean test` 保证不回归（84/84 绿）；再写了个**运行时探针**——现场生成一个带文字的 PDF、再用同样的 API 抽回，断言抽到的文字和写进去的一模一样（`MATCH=true`）。**光'能编译'不代表'能工作'。**"

## 附：顺手修掉的一个"环境相关"脆弱测试

`ApiContractTest.llmOptionsFallsBackWhenOllamaUnavailable` 原本**真的去连本机 Ollama**（`/api/tags`）：

- 本机**没跑 Ollama** → 走"回落"分支 → 断言 `qwen3:8b` 通过；
- 本机**跑了 Ollama** → 返回真实模型清单（本机是 `qwen3.5:2b`）→ **断言失败**。

→ 这是"**测试结果取决于运行环境**"的坏味道，违背契约测试"**零外部依赖、结果确定**"的原则。

修法：加 `@MockitoBean LlmConnectivityService` 替身，在用例里显式让它返回空列表（等价于"Ollama 不可达"），
**结果从此确定**。安全性已核对：该服务只被 `/api/llm-options` 与 `/api/llm-config/local-models` 使用，后者测试未覆盖。

**面试怎么答**："我发现有个用例会因为'我本机是否开着 Ollama'而时红时绿。**测试必须是确定的**，
所以我用替身把外部依赖钉死，让它稳定地覆盖'回落'这条分支——顺带把'环境相关'这个隐患从构建里除掉了。"

## P0-3　知识库导入：docx 解析失败，一个文档只分成一段

> 现象（用户反馈）：**知识库导入文件解析不成功，一个文档只分成一段**。

### 3.1 排查过程（从现象到根因，全程用证据说话）

**第一步：查数据库，拿第一手事实**（不猜）。两条 SQL：

```sql
SELECT id, filename, size, CHAR_LENGTH(content) AS content_chars FROM files;
SELECT file_id, COUNT(*) chunks, chunk_text FROM kb_chunks GROUP BY file_id;
```

结果非常刺眼：

| 文件 | 磁盘大小 | 抽到的正文字数 | 片段数 |
|---|---|---|---|
| 安徽理工大学学生违纪处分办法.docx | 20681 B | **22** | 1 |
| 安徽理工大学校内资助经费管理办法.docx | 39145 B | **22** | 1 |

**20KB 的文档只抽出 22 个字** → 说明**抽取环节就失败了**，根因不在切分器。

**第二步：把 `content` 打出来看** → 两个文件都是同一句提示：

```
（Word 文档未提取到文本，可能是空文档）
```

**第三步：写探针复现并定位**（只看"能编译"是不够的）。探针做了三件事：
1. 校验文件头 `magic`；
2. 列出 zip 条目，确认有没有 `word/document.xml`；
3. 用**与 `FileService.extractDocx` 完全相同**的逻辑抽取两遍，只切换一个开关。

```
magic=504B  -> ZIP(真 docx)
zip_entries=17  has_word/document.xml=true
nsAware=false(现状)  len=0        ← 一个字都抽不到
nsAware=true (修复)  len=7196     ← 正常抽出
```

### 3.2 根因（三层，逐个说清）

**① 主因：`DocumentBuilderFactory` 忘了开"命名空间感知"**

```java
// 旧代码
var doc = DocumentBuilderFactory.newInstance().newDocumentBuilder().parse(...);
var ps = doc.getElementsByTagNameNS("*", "p");   // ← 按命名空间查
```

- `DocumentBuilderFactory.newInstance()` **默认 `namespaceAware=false`**；
- 此时解析器**不解析命名空间**，元素的 `localName` 为空；
- 而 `getElementsByTagNameNS("*","p")` 是**按 localName 匹配**的 → **一个节点都匹配不到** → 文本为空；
- 结果：**所有正常 docx 都抽不出一个字**（不是个别文件的问题）。

**② 次因：失败时返回"人话提示"当正文，污染了知识库**

- 抽取失败时返回 `"（Word 文档未提取到文本，可能是空文档）"`；
- 这句提示被**当成正文**存进 `files.content`，又被切分、向量化、写进 `kb_chunks`
  （数据库里看到的 `chunk_text` 就是它）→ **RAG 会把这句提示当"知识"检索出来**；
- 而 `extractText` 的注释**白纸黑字**写着契约：*"抽取不到返回空串（不会返回报错文本，避免把报错当正文索引进库）"* ——
  `extractDocx` **违反了它自己的契约**。

**③ 我上次的 P0-2 修得不彻底：`isIndexable` 仍把 PDF 挡在门外**


## P0-4　会话功能两连修：云端模型"接入却报错" + 本地模型"输出一半卡住"

> 现象（用户反馈）：① 接入的大模型用不了、会报错；② 本地模型输出一半就卡住。

### 4.1 先拿实证（数据库）

```sql
SELECT id,user_id,name,base_url,model FROM llm_providers;
SELECT id,conversation_id,provider,model,CHAR_LENGTH(content),LEFT(content,36) FROM messages WHERE role='assistant' ORDER BY id DESC;
```

| 证据 | 值 |
|---|---|
| 接入的云端 | `base_url = https://ws-g2je…cn-beijing.maas.aliyuncs.com/compatible-mode/v1`，model=`qwen-plus` |
| 云端两条消息 | 内容都是 **`(回答生成已中断)`**（9 字）→ **一个字都没吐就报错** |
| 本地一条消息 | 内容 **33 字、停在"…有什么"** → **句尾被截断** |

### 4.2 根因 A：`base_url` 约定不一致 → 聊天请求变成 `…/v1/v1/chat/completions`

**从 Spring AI 的 jar 里查到的默认常量**（不是猜的）：

```
DEFAULT_BASE_URL         = "https://api.openai.com"      ← 不含 /v1
DEFAULT_COMPLETIONS_PATH = "/v1/chat/completions"        ← 自己会补 /v1
```

于是两条路径对 `base_url` 的预期正好相反：

| 路径 | 请求 URL（base 带 `/v1` 时） | 结果 |
|---|---|---|
| **测连** `LlmConnectivityService`：`baseUrl + "/chat/completions"` | `…/compatible-mode/v1/chat/completions` | ✅ 通过 → **所以能保存** |
| **聊天** `ChatModelFactory`（走 Spring AI，自己补 `/v1`） | `…/compatible-mode/**v1/v1**/chat/completions` | ❌ **404 报错** |

> 这就完美解释了那个诡异现象：**保存时测连通过、一聊天就报错**。
> 而用户填 `/v1` 是完全合理的 —— 界面占位符给的就是 `…/compatible-mode/v1`。

**修复**：新增 `ModelCatalog.normalizeOpenAiPrefix(baseUrl)` —— 去掉结尾 `/`、并把结尾的 `/v1` 统一剥掉，
让两边都基于**同一个"不含 /v1 的前缀"**去拼路径：测连拼 `前缀 + /v1/chat/completions`，
聊天交给 Spring AI 的默认 `/v1/chat/completions`。两种填法（带 /v1、不带 /v1）从此等价。

### 4.3 根因 B：`ChatService` 漏调 `splitter.flush()`（实现遗漏）

对照参考实现，收尾处**明确有一句**：

```python
# 收尾：冲掉标签拆分器缓冲里的残留
think, answer = splitter.flush()
```

而 Java 版 `ChatService` **只 `feed`、从不 `flush`**。为什么这会造成"输出一半就停"：
`ThinkSplitter.feed()` 每帧都会**故意保留末尾若干字符**（怕 ` thinking` 标签跨帧被拆断），
所以流结束时缓冲里**一定还留着东西**。不 flush 的后果：

1. **回答结尾被吃掉几个字** → 用户看到"输出到一半就停住"；
2. 若模型开了思考却没吐结束标签，**缓冲里的正文整段丢失**（更严重）。
3. 而且 `persistAssistant` 落库的是没 flush 的 `answer` → **数据库里存的也是缺尾的**（与证据一致）。

**修复**：`onComplete` 增加 `ThinkSplitter` 参数，在**回写正文之前** `flush()`，
把残留按"思考/正文"分路推给前端并追加进 `answer`。

### 4.4 修复清单

| # | 文件 | 改动 |
|---|---|---|
| 1 | `common/ModelCatalog.java` | 新增 `normalizeOpenAiPrefix(baseUrl)`（去尾 `/`、剥尾 `/v1`） |
| 2 | `service/LlmConnectivityService.java` | 测连与 `/v1/models` 都改用归一化前缀 |
| 3 | `service/llm/ChatModelFactory.java` | `OpenAiApi.baseUrl(normalizeOpenAiPrefix(baseUrl))`，消除双 `/v1` |
| 4 | `service/ChatService.java` | `onComplete` 收尾 **`splitter.flush()`**，且先追加进 `answer` 再落库 |

### 4.5 怎么验证

**探针（直接调用编译产物里的真实类）**：

```
==== 1) ThinkSplitter：不 flush vs flush ====
不 flush（旧行为）=[你好，我可以帮你做这些： 1. 查询天气；2. 记待办；3. 查知识库]   len=35   ← 结尾被吃掉
flush 后（修复）  =[你好，我可以帮你做这些： 1. 查询天气；2. 记待办；3. 查知识库。请问需要什么？]  len=43  ← 完整

==== 2) 云端 URL ====
输入=…/compatible-mode/v1  →  归一化=…/compatible-mode
   聊天URL=…/compatible-mode/v1/chat/completions   一致=true（与测连完全相同，不再 v1/v1）
输入=https://api.deepseek.com  →  聊天URL=https://api.deepseek.com/v1/chat/completions  一致=true
```

`mvn clean test` → **84/84 全绿，BUILD SUCCESS**。

### 4.6 面试验问答

**Q1：用户说"云端模型能保存、一聊天就报错"，你怎么查？**

**Q5：归一化前缀会不会有副作用？**

## P0-5　点「重新生成」报 `InvalidDataAccessApiUsageException`（事务自调用失效）

> 现象：会话里点**重新生成**，前端弹「服务器内部错误：InvalidDataAccessApiUsageException」。

### 5.1 怎么定位的（拿运行中的真实堆栈）

后端把日志只打到控制台，所以我**另起一个实例（不同端口）并把输出重定向到文件**，再逐个复现用户动作。
只读接口 20 个全 200；建/删技能、会话、知识库、上传 `.md`、重索引、普通聊天全部正常；
**只有 `regenerate:true` 复现了**，日志里拿到完整堆栈：

```
org.springframework.dao.InvalidDataAccessApiUsageException:
  No EntityManager with actual transaction available for current thread - cannot reliably process 'remove' call
    at $Proxy143.deleteByConversationIdAndRoleAndIdGreaterThan
    at com.ipas.assistant.service.ChatService.prepare(ChatService.java:222)   ← ★
    at com.ipas.assistant.service.ChatService.stream(ChatService.java:132)
```

### 5.2 根因：`@Transactional` 被"静默忽略"（两个叠在一起的坑）

`ChatService.prepare` 上有 `@Transactional`，但它**从未生效**，原因是两条：

1. **同类自调用**：`stream()` 里写的是 `prepare(...)`（等价 `this.prepare(...)`）。
   Spring 的事务靠**动态代理**织入，自调用**不经过代理** → 事务不存在。
2. **方法不是 public**：它当时是 `protected`。Spring 官方明确：
   *代理模式下 `@Transactional` 只对 public 方法生效，标在 protected/private 上不报错，但配置被忽略。*

于是 `prepare` 里的写操作跑在"没有事务的线程"上。为什么**只有"重新生成"会炸**：
那条分支调用了 **`deleteBy...` 派生删除**，而派生删除**不像 `save()` 那样自带事务**
（`SimpleJpaRepository` 的 CRUD 自带 `@Transactional`，派生方法没有），必须依赖外层事务；
普通发送只用到了 `save()`，所以看起来"没事"。

> 排查结论：全项目**仅此一处** `@Transactional` 标在非 public 方法上（已用正则全量确认）。

### 5.3 修复

| # | 文件 | 改动 |
|---|---|---|
| 1 | `service/ChatService.java` | `prepare` 由 `protected` 改 **`public`** |
| 2 | 同上 | 新增 **`@Lazy ChatService self` 自注入**，调用改为 `self.prepare(...)`，让调用**经过代理** |
| 3 | 同上 | `Prepared` 由 `private record` 改**包级**（public 方法的返回类型不该更隐蔽） |

（`@Lazy` 用于打破"自己注入自己"的循环依赖：注入的是延迟代理，构造阶段不会真的获取自身。）

### 5.4 怎么验证

**重放同一个操作**（重启实例后）：

| | 修复前 | 修复后 |
|---|---|---|
| `POST /api/chat/stream` + `regenerate:true` | `{"detail":"服务器内部错误：InvalidDataAccessApiUsageException"}` | 正常流式输出，结尾 `"done":true` ✅ |
| 是否仍报 500 | 是 | **否** |

外加 `mvn clean test` → **84/84 全绿**。

### 5.5 面试问答

**Q1：`@Transactional` 什么情况下会失效？**
> "常见四种：①**同类自调用**（`this.xxx()` 不走代理）；②**方法非 public**（代理只拦 public，标在 protected/private 上会被静默忽略）；③异常被 catch 没抛出（默认只对 RuntimeException 回滚）；④方法不是被 Spring 管理的 Bean 调的。这次我踩的是 ①+② 同时发生。"

**Q2：为什么"普通发送"没事，"重新生成"才炸？**
> "因为 `save()` 是 `SimpleJpaRepository` 的 CRUD，**方法自带 `@Transactional`**，没有外层事务也能work；而 `deleteBy...` 是**派生删除方法，不带事务**，必须有外层事务。所以同一个方法里，事务失效只会在"用了派生删除"的分支暴露出来——**这种'只在某条分支才炸'的 bug 最容易漏测**。"

**Q3：怎么定位的？**
> "光看代码我没敢下结论，于是**起了个带日志落盘的实例**，把用户的动作逐个复现：只读接口、增删改、上传、聊天全试一遍，只有 `regenerate` 复现，日志里直接给出堆栈指到 `ChatService.prepare` → 一眼看出是代理没走到。"

**Q4：怎么防止再犯？**
> "两条纪律：① **`@Transactional` 只写在 public 方法上，且只由别的 Bean 调用**（同类内部要复用得抽成独立 Bean，或自注入代理）；② **派生删除/`@Modifying` 这类"不自带事务"的方法要格外小心**，它们要么在外层事务里，要么自己在 Repository 方法上标 `@Transactional`。"

## P0-6　两个 SSE / 索引收尾 bug：停止按钮不复位 + "重建全部"无效

> 用户反馈：① 回答已生成完，但聊天框的**停止按钮不更新**；② 老的破损文档**单个/全部重建都无变化**，仍是一个文档一个片段。

### 6.1 问题 ①：停止按钮卡住 —— SSE 连接没有被"无条件关闭"

**前端机制**：停止按钮由 `streamingSids` 派生（`loading = streamingSids.has(sessionId)`），
而它是在流函数的 **`finally`** 里被移除的 —— 也就是说，**前端必须"读到流结束"才会复位按钮**。

> ### ⚠️ 更正（重要）
> 本节原先把根因写成"`emitter.complete()` 被跳过"——**那是错的**。它确实是健壮性隐患（也确实值得修），
> 但我修完之后**按钮依旧卡住**。真正根因是 **`Connection: keep-alive` 导致代理上游收不到响应结束**，
> 见下面的 **6.1.1**。保留下面的分析，是为了记录"差一点就找错方向"的排查过程。

**原先的判断（×，不是本次根因）**：`ChatService.onComplete` 里，`emitter.complete()` 被放在一个**只 `catch (IOException)`** 的 try 内：

```java
try {
    maybeEmitSources(...);
    emitter.send(done);
    emitter.complete();          // ← 前面的 send 一旦抛非受检异常，这行就被跳过
} catch (IOException e) { ... }  // ← 只接 IOException，接不住 IllegalStateException
```

而 `emitter.send(...)` 在**客户端已断开 / emitter 已关闭**时会抛 **`IllegalStateException`**（非受检），
于是 `complete()` 永远不会执行 → HTTP 连接一直挂着 → 直到 **`SSE_TIMEOUT_MS`（本类里是 10 分钟）** 才断。
前端在这 10 分钟里读不到"流结束"，**按钮就一直卡在「停止」**。`onError` 分支同样有此问题。

> 另需**自我检讨**：上一轮为了修"输出一半停住"，我在 `onComplete` 开头加了 flush 发送，
> 又新增了一条"可能中断收尾"的路径，加重了这个问题。

**修复（`service/ChatService.java`）**：

| 改动 | 说明 |
|---|---|
| 新增 `safeSend(emitter, Object)` | 发送一帧，**任何异常只记日志、绝不外抛**（收尾不能被某一帧打断） |
| 新增 `completeQuietly(emitter)` | **无条件**关闭 emitter，已关闭/已出错时的异常一律忽略 |
| `onComplete` 重构 | done 事件单独 try，**`completeQuietly` 放进 `finally`** |
| `onError` 重构 | `memory.clearMemory` 单独 try；`completeQuietly` 放进 `finally` |
| `onAbort` | 清记忆失败也不再打断后续清理 |

**原则**：**"关闭连接"必须是无条件的**，不能依赖前面若干次发送都成功。

### 6.1.1 ★ 真正的根因：SSE 走 keep-alive，代理（Node）收不到"响应结束"

**排查过程 —— 先做"直连 vs 走代理"的对照**（这是定位的关键一步）：

| 路径 | 收到 done 事件 | 响应是否结束 |
|---|---|---|
| **直连后端 8002** | ✅ | ✅ **1.1~1.4 秒正常关闭** |
| **走 Vite 代理 5174** | ✅（数据全送达） | ❌ **永远不结束**（curl 一直挂到超时） |

**为什么代理不结束？** 因为 Vite 代理（http-proxy）的上游就是 **Node 的 http 客户端**。
我写了一个 Node 探针，分别对"旧代码/新代码"发同一个 SSE 请求，看它是否触发 `end`：

| 目标 | 响应头 `Connection` | Node 客户端结果 |
|---|---|---|
| 旧代码（修复前） | `keep-alive` | ⚠️ **未触发 `end`**（26.8s 才被 close 兜底） |
| 新代码（修复后） | **`close`** | ✅ **触发 `end`，响应正常结束**（13.2s） |

**结论**：`SseEmitter.complete()` 只是结束了**消息体**，但连接仍是 **keep-alive** 不关闭；
Node 客户端因此认为响应还没完 → 代理不结束下游 → **浏览器 `fetch` 的 reader 永远拿不到 `done`**
→ `ChatWindow` 里清除 `streamingSids` 的 `finally` 永远不执行 → **停止按钮一直卡在「停止」**。

> 补充：同一台机器上 **Vite 只监听 `::1`（IPv6）**、**后端只监听 `127.0.0.1`（IPv4）**，
> 所以前端必须写 `127.0.0.1` 作为代理目标、用 `localhost` 访问前端 —— 这一点项目注释里已有说明。

**修复（`controller/ChatController.java` → `stream` 方法）**：

```java
// 改前
@PostMapping("/stream")
public SseEmitter stream(...) {
    return chatService.stream(me.id(), body);
}

// 改后
@PostMapping("/stream")
public ResponseEntity<SseEmitter> stream(...) {
    SseEmitter emitter = chatService.stream(me.id(), body);
    return ResponseEntity.ok()
            .contentType(MediaType.TEXT_EVENT_STREAM)   // 固定 SSE 类型（避免被推断成 json）
            .header(HttpHeaders.CONNECTION, "close")    // ★ 流结束即真正关闭连接
            .body(emitter);
}
```

**顺带的两处加固**（不是根因，但有用）：
- `service/ChatService.java`：`safeSend` / `completeQuietly`，让收尾不被某一帧的失败打断。
- `frontend/vite.config.ts`：代理改为对象配置，加 `Cache-Control: no-transform`、`X-Accel-Buffering: no`，
  并在上游 `end` 时显式 `res.end()` —— 保证 SSE 不被中间层缓冲。

**验证方式**：重启后端后，用「直连 / 走代理」两条路径各跑一次 SSE，确认**都会结束**；
浏览器里则表现为：答案生成完 → 输入框右侧**自动恢复为「发送」**。

### 6.2 问题 ②：「重建全部」无效 —— 用的是库里那份"已经坏掉的正文"

`KbService.reindexAll` 早前实现（沿用 `reindex_all` 的思路）：

```java
// KbService.java:309-310（旧）
String content = (f.getContent() == null ? "" : f.getContent());   // ← 直接用 DB 里的 content
indexFile(userId, f.getId(), content, f.getCollectionId());
```

那份 `content` 是**上传那一刻一次性抽好的**。当那次抽取本身是坏的
（例如历史上 docx 抽取整体失败，存下来的其实是"（Word 文档未提取到文本）"这句兜底提示，只有 22 字），
用它重建就只是**把同一份错内容再切一遍** → 片段数一点不变 → 用户看到"重建全部毫无改动"。

> 单文件 `reindex` 本来是好的（它读磁盘重抽）—— 我实测确认过：对老文件点单文件重建，
> `content 22 → 21733`、片段 `1 → 51`。问题只出在"重建全部"。

**修复**：

| 文件 | 改动 |
|---|---|
| `service/FileService.java` | **新增 `reindexAll(userId)`**：逐个文件「读磁盘 → `extractBody` 重抽 → `indexFile` → 回写 content」；单个失败不影响其它，返回成功/失败数。放在 FileService 是因为只有它同时具备"读磁盘 + 抽正文"能力（`KbService` 反向依赖它，不能循环） |
| `service/KbService.java` | 移除旧 `reindexAll`，留注释指向新位置 |
| `controller/KbController.java` | `POST /api/kb/reindex-all` 改调 `fileService.reindexAll(...)` |

### 6.4 面试问答

**Q1：前端按钮不刷新，怎么判断是前端还是后端的锅？**
> "先看**状态的来源**：这个按钮由 `streamingSids` 派生，而它在流函数的 `finally` 里被清掉 —— 说明**只要前端读到"流结束"就会复位**。于是问题就变成"流到底有没有正常关闭"，用 curl 挂 `-w time_total` 一测就知道：连接是正常关闭还是拖到超时。"

**Q2：`SseEmitter` 收尾要注意什么？**
> "一句话：**关闭必须是无条件的**。`complete()` 千万别写在"只 catch 部分异常"的 try 里，也别让它依赖前面几次 `send` 都成功 —— 客户端断开时 `send` 会抛 `IllegalStateException`（非受检），你一不留神 `complete()` 就被跳过，连接会一直挂到超时。正确做法是：**每次 send 都自己吞异常，`complete()` 放 `finally`。**"

**Q3：为什么"单文件重建"没问题、"重建全部"却不行？**
> "因为两者取正文的来源不同：单文件重建是**从磁盘重新抽**（所以能救回解析逻辑修好之前的老文件），而"重建全部"当初直接用了 **DB 里存的那份 content**（上传时一次性抽好的）。那份 content 本身是坏的（22 字的兜底提示），再切一遍当然还是 1 段。**修法是把"重建全部"也改成读磁盘重抽**，两者行为统一。"

**Q4：这次修复怎么定位的？**
> "问题 ② 是**查数据库**发现的：老文件的 `content` 只有 22 字，一眼就看出"重建用的是坏正文"。问题 ① 是**读前端状态流转**：按钮由"流结束"驱动，于是把排查范围收敛到"后端有没有关连接"，最后在 `onComplete` 的 try/catch 结构里找到漏网路径。**先定位"状态由谁驱动"，再顺藤摸瓜，比盲猜快得多。**"
