## 模块 1 Java 基础

### 1.1 集合
**Q：ArrayList 和 LinkedList 区别？HashMap 底层？**
- **简洁版**：ArrayList 底层数组，随机访问 O(1)、中间增删 O(n)；LinkedList 双向链表，头尾增删 O(1)、随机访问 O(n)。HashMap 底层是"数组 + 链表 + 红黑树"：key 经 `hash()` 扰动后 `(n-1)&hash` 定位桶，链表长度 ≥8 且数组 ≥64 时转红黑树，负载因子 0.75，扩容翻倍并 rehash。
- **追问**：为什么容量是 2 的幂？→ 让 `(n-1)&hash` 等价取模且分布均匀。为什么 0.75？→ 时间/空间折中。线程安全吗？→ 不安全，用 `ConcurrentHashMap`。
- **结合本项目**：实体里的 `List<Long>` 字段（如会话勾选的技能/知识库 id）通过 `entity/converter/LongListJsonConverter` 存成 JSON 列；`AgentCache` 的缓存键里对 id 集合**排序后再用**，因为"顺序不同 = 不同键"会导致缓存反复失效。
- **✅加分**：能说出"扩容时 JDK8 用尾插避免成环"、"ConcurrentHashMap 用 CAS+synchronized 锁桶"。
- **⚠️避坑**：别说"HashMap 线程安全"，也别说"ConcurrentHashMap 允许 null 值"（不允许）。

### 1.2 泛型
**Q：什么是泛型擦除？为什么要有通配符？**
- **简洁版**：泛型只在**编译期**做类型检查，运行时被擦除成 `Object`（`List<String>` 与 `List<Integer>` 运行时是同一个类）。通配符 `? extends T`（上界，只能读）/`? super T`（下界，只能写），口诀 **PECS**（Producer Extends, Consumer Super）。
- **追问**：为什么不能 `new T[]`？→ 擦除后无法确定类型，运行时数组要具体类型。
- **结合本项目**：`AgentCache.Key` 用 `record`（不可变）做复合键、`List<Long>` 参与键的相等判断，天然利用泛型做类型安全，避免"拼字符串键"的歧义（`[2,3]` 与 `[23]` 分不清）。
- **✅加分**：能举"拼字符串做缓存键"的真实 bug，说明泛型 + record 更安全。
- **⚠️避坑**：别把"擦除"说成"运行时没有类型信息"——反射仍能拿到泛型签名（`ParameterizedType`）。

### 1.3 异常
**Q：受检异常和非受检异常？finally 与 return 的执行顺序？**
- **简洁版**：`Exception` 分受检（`IOException`，编译强制处理）与非受检（`RuntimeException`，如 NPE）。`finally` 一定执行（除非 JVM 退出），且"finally 里的 return 会覆盖 try 里的 return"。
- **追问**：try-with-resources？→ 自动关闭实现 `AutoCloseable` 的资源，比手写 finally 更安全（异常抑制）。
- **结合本项目**：`common/ApiException` 是**运行时异常**；`GlobalExceptionHandler` 统一把它翻译成 `{"detail":"..."}` + 正确状态码。曾踩坑：把"构造模型"也包进 try，导致 **400（客户端配置缺 Key）被误包成 500**；修法是**构造放 try 外，只把真正的模型调用包进 try**。
- **✅加分**：能讲"业务异常 vs 系统异常要分开，配置缺失是 400 不是 500"。
- **⚠️避坑**：别再写 `catch (Exception e) {}` 吞异常（本项目早期就因此把语义吞掉了）。

### 1.4 IO / 反射 / 注解
**Q：BIO/NIO/AIO？反射有什么用？注解怎么生效？**
- **简洁版**：BIO 阻塞、NIO 多路复用（`Selector`）、AIO 异步回调。反射能在运行期获取类信息/调用方法（框架的基石）。注解本身只是"标记"，靠**反射读取 + 框架处理**才生效（运行时注解用 `RetentionPolicy.RUNTIME`）。
- **结合本项目**：①`AssistantTools` 的方法加 **`@Tool`**，SAA 通过反射把它们暴露成模型可调用的工具；②`JwtAuthenticationFilter` 反射式解析 token 里的 claims；③`@Entity/@Table` 由 Hibernate 启动时反射扫描建映射。
- **✅加分**：能说"Spring 全靠反射 + 注解 + 动态代理把对象装配起来"。
- **⚠️避坑**：反射有性能开销，别在热点循环里反复 `getDeclaredMethod`。

## 模块 2 JVM

**Q2.1 JVM 运行时内存结构？**
- **简洁版**：**线程私有**——程序计数器、虚拟机栈（栈帧：局部变量表/操作数栈）、本地方法栈；**线程共享**——堆（对象）、方法区（JDK8 起用**元空间**，在本地内存）。
- **追问**：字符串常量池在哪？→ JDK7 后移到堆里。
- **结合本项目**：`-XX:+HeapDumpOnOutOfMemoryError` 建议加上；本项目是**长驻 Web 服务**，堆里最占内存的是 Spring 单例 Bean 与缓存（如 `AgentCache`、`RagSourcesBus` 的 `ConcurrentHashMap`）。
- **✅加分**：强调本项目**持久域驻留**要注意缓存不能无界（见 2.5）。

**Q2.2 垃圾回收怎么判断"对象死了"？有哪些 GC 算法？**
- **简洁版**：用**可达性分析**（从 GC Roots 出发，不可达即回收），不用引用计数（解决循环引用）。三大算法：标记-清除（碎片）、复制（浪费一半，用于新生代）、标记-整理（无碎片，用于老年代）。**分代收集**：新生代 Minor GC（Eden+S0/S1，对象熬过 15 次进入老年代），老年代 Major/Full GC。
- **追问**：常见收集器？→ Serial / ParNew / Parallel / CMS / **G1**（JDK9+ 默认，可预测停顿）/ ZGC（低延迟）。
- **结合本项目**：JDK21 默认 **G1**；本项目 QPS 低，不必调 GC，但答辩时能说出"G1 分 Region、按停顿目标回收"就很加分。
- **✅加分**：能讲"对象优先在 Eden 分配、大对象直接进老年代、动态年龄判断"。

**Q2.3 OOM 怎么排查？**
- **简洁版**：定位类型（堆/元空间/栈/直接内存）→ 看日志与 `-XX:+HeapDumpOnOutOfMemoryError` 生成的 dump → 用 **MAT/JVisualVM** 分析支配树找大对象 → 结合 `jstat` 看 GC 频率、`jstack` 看线程。
- **结合本项目**：本项目里最可能的 OOM 源是**无界缓存**与**大模型返回的超长文本**入内存；所以 `RagSourcesBus` 在会话结束时 `unregister` 清理，`max-total-chunks=30` 限制单次检索片段数。
- **✅加分**：能说出"先看是不是内存泄漏（老年代持续增长且 Full GC 后不降），再谈调大堆"。

**Q2.4 类加载机制与双亲委派？**
- **简洁版**：加载→验证→准备→解析→初始化。**双亲委派**：类加载器收到请求先交给父加载器，父加载不到才自己加载；好处是**安全**（核心类不被篡改）+**避免重复加载**。打破场景：JDBC 的 SPI（`Thread.currentThread().getContextClassLoader()`）、Tomcat 应用隔离。
- **结合本项目**：`mysql-connector-j` 就是通过 SPI 注册 `Driver` 的典型例子。
- **✅加分**：能举"JDBC 用线程上下文类加载器打破双亲委派"。

**Q2.5 常用 JVM 参数？**
- **简洁版**：`-Xms/-Xmx`（堆初始/最大，建议设相等避免抖动）、`-Xmn`、`-XX:MetaspaceSize`、`-XX:+UseG1GC`、`-XX:+HeapDumpOnOutOfMemoryError`、`-XX:HeapDumpPath`、`-Xss`（栈大小）。
- **结合本项目**：`run.sh/run.bat` 启动可通过 `JAVA_OPTS` 追加；答辩可答"生产会把 Xms=Xmx 设成 1~2G，其余交给 G1"。
- **⚠️避坑**：别把 `-Xmx` 设得超过物理内存（会触发 swap 甚至被系统 OOM Killer 杀）。

## 模块 3 多线程与并发

**Q3.1 线程池的核心参数与执行流程？**
- **简洁版**：7 参数——核心线程数、最大线程数、空闲存活时间、时间单位、**工作队列**、线程工厂、**拒绝策略**（AbortPolicy 默认 / CallerRuns / Discard / DiscardOldest）。流程：核心线程满 → 入队 → 队列满才扩到最大线程 → 再满则拒绝。
- **追问**：为什么不推荐 `Executors.newFixedThreadPool`？→ 用无界队列（`LinkedBlockingQueue`）可能 OOM；应手写 `ThreadPoolExecutor` 控队列。
- **结合本项目**：Spring MVC 用内嵌 Tomcat 的线程池处理请求（**一请求一线程**）；大模型调用是**阻塞 IO**，所以放在 Tomcat 工作线程里等待；数据库侧由 **HikariCP** 连接池管理（`max=20`），线程数要和连接池匹配，否则"线程排队抢连接"。
- **✅加分**：能说出"IO 密集型线程数可设为 CPU 核数×2 左右，CPU 密集型 ≈ 核数+1"。

**Q3.2 synchronized 与 Lock 的区别？锁升级？**
- **简洁版**：`synchronized` 是 JVM 关键字、自动释放、非公平；`ReentrantLock` 是 API、手动 `unlock`（放 finally）、可公平/可中断/可超时。锁升级（JDK6+）：**无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（OS 互斥）**。
- **结合本项目**：`MysqlConversationMemory` 等对共享状态的操作用 `synchronized`/`ConcurrentHashMap` 保证线程安全；`RagSourcesBus` 用 `ConcurrentHashMap<Long,List<...>>` 而非 `ThreadLocal`，因为工具执行与事件回调**可能不在同一线程**。
- **✅加分**：能解释"为什么不用 ThreadLocal——Reactor 线程模型下上下文会跨线程丢失"。

**Q3.3 volatile / CAS / AQS？**
- **简洁版**：`volatile` 保证**可见性 + 禁止指令重排**，**不保证原子性**（`i++` 仍不安全）。CAS（比较并交换）无锁原子操作，ABA 问题用版本号解决。AQS 是 `AbstractQueuedSynchronizer`：一个 `volatile int state` + CLH 双向队列，`ReentrantLock/CountDownLatch/Semaphore` 都基于它。
- **结合本项目**：`ChatService` 用 `AtomicBoolean` 保证 `sources` 事件只发一次；`agent.streamMessages(...).subscribe(...)` 返回 `Disposable` 用于断连时取消。
- **✅加分**：能说"单例的 DCL 写法里 `volatile` 是必须的"。

**Q3.4 并发容器 / CompletableFuture？**
- **简洁版**：`ConcurrentHashMap`（分段/桶级锁 + CAS）、`CopyOnWriteArrayList`（读多写少）、`BlockingQueue`（生产者消费者）。`CompletableFuture` 支持编排（`thenApply/thenCompose/allOf`）与异步回调。
- **结合本项目**：SSE 流式返回其实用到了 **Reactor**（`Flux`，SAA 图运行时的输出），`ChatService` 对其 `subscribe` 做逐帧处理；`CompletableFuture` 在本项目用于把"阻塞的模型调用"包成异步（SAA 内部大量使用）。
- **✅加分**：能把"响应式（Reactor）与线程池阻塞模型"的区别讲清。

## 模块 4 Spring

**Q4.1 IoC 和 DI 是什么？**
- **简洁版**：IoC（控制反转）= 对象的创建与依赖交给容器管；DI（依赖注入）是它的实现方式（构造器/Setter/字段注入）。好处：解耦、可测试、可统一管理生命周期。
- **结合本项目**：全项目**构造器注入**（`NoteService(NoteRepository repo, ...)`），好处是不可变、便于测试（测试里 `@MockitoBean` 替换依赖）。启动时 Spring 扫描 `@Service/@Repository/@RestController` 生成 Bean。
- **✅加分**：能说"构造器注入能暴露循环依赖问题，字段注入会掩盖它"。

**Q4.2 AOP 是什么？动态代理两种方式？**
- **简洁版**：AOP（面向切面）= 把日志、事务、鉴权这类**横切关注点**从业务里抽出来。实现：JDK 动态代理（基于接口）或 CGLIB（基于继承，子类代理）。Spring Boot 2.x+ 默认**CGLIB**。
- **结合本项目**：`@Transactional` 就是 AOP 代理实现的；`ScheduleReminderJob` 的定时执行、`GlobalExceptionHandler` 的统一异常处理都是"横切"思想。**避坑**：同类内部方法自调用会让 `@Transactional` 失效（不走代理）。
- **✅加分**：能举"`@Transactional` 失效的三种场景：自调用、private 方法、异常被吞"。

**Q4.3 Bean 生命周期？**
- **简洁版**：实例化 → 属性填充（依赖注入）→ `Aware` 接口回调 → `BeanPostProcessor.postProcessBeforeInitialization` → `@PostConstruct`/`InitializingBean` → `BeanPostProcessor.postProcessAfterInitialization`（**AOP 代理在此生成**）→ 使用 → `@PreDestroy`。
- **结合本项目**：`DataDirProvider`、`AgentFactory` 等都是单例 Bean；`MysqlSaver` 在**构造时就连库**，所以 `config/AgentMemoryConfig` 加了 `@Profile("!test")`，测试环境整体不装配它。
- **✅加分**：能说"代理对象在初始化后才生成，所以注入的是代理"。

**Q4.4 循环依赖？三级缓存？**
- **简洁版**：A 依赖 B、B 依赖 A。Spring 用**三级缓存**解决**单例 + 字段/Setter 注入**的循环依赖：一级存成品、二级存半成品、三级存对象工厂（用于提前暴露代理）。构造器注入的循环依赖**解决不了**（直接报错）。
- **结合本项目**：项目里没有循环依赖（构造器注入 + 分层单向依赖），这正是"构造器注入"的收益。
- **⚠️避坑**：别答"Spring 能解决所有循环依赖"。

**Q4.5 `@Transactional` 传播行为 / 失效场景？**
- **简洁版**：常用 `REQUIRED`（默认，有事务加入、没有新建）/`REQUIRES_NEW`（挂起当前、新建独立事务）/`NESTED`。失效场景：**自调用**、方法非 public、异常被 catch 未抛、传播写错、数据库引擎不支持。
- **结合本项目**：`ChatService.prepare` 加了 `@Transactional`，把"落用户消息 + 预建助手消息 + 首轮命名"放在一个事务里；踩坑：`updated_at` 由 `@PreUpdate` 维护，但**事务未提交时它是旧值**，所以服务里显式 `repository.flush()` 后再构造响应。
- **✅加分**：能讲"flush 让 `@PreUpdate` 立即触发，否则接口返回旧时间戳"。

**Q4.6 Spring MVC 请求流程？**
- **简洁版**：请求 → `DispatcherServlet` → `HandlerMapping` 找到 Controller → `HandlerAdapter` 调用 → 参数绑定（`@RequestBody` 走 `HttpMessageConverter`，如 Jackson）→ 返回值处理 → 写响应。
- **结合本项目**：Jackson 配了 `property-naming-strategy=SNAKE_CASE`，所以 Java 的 camelCase 自动输出为 `snake_case`，**保证前端契约不变**。
- **✅加分**：能说"`@RestController` = `@Controller` + `@ResponseBody`"。

## 模块 5 Spring Boot

**Q5.1 自动配置原理？**
- **简洁版**：`@SpringBootApplication` 里的 `@EnableAutoConfiguration` 通过 `AutoConfiguration.imports`（Boot 2.7+，旧版是 `spring.factories`）加载一堆自动配置类，再用 `@ConditionalOnClass/@ConditionalOnMissingBean/@ConditionalOnProperty` 按条件生效。
- **结合本项目**：本项目**主动不用** Spring AI 的 starter 自动配置——因为模型是"运行时按会话动态构造"的，自动配置出来的单例 `ChatModel` 用不上，还会因"要求必配 api-key"导致"只用本地 Ollama"时**启动失败**。所以直接依赖实现类，自己 `new`（`service/llm/ChatModelFactory`）。
- **✅加分**：能说清"什么时候该用 starter、什么时候该绕过自动配置"——这是很真实的工程判断。

**Q5.2 starter 是什么？启动流程？**
- **简洁版**：starter = 一组依赖的"打包入口"（如 `spring-boot-starter-web` = web + tomcat + jackson）。启动流程：`SpringApplication.run` → 准备 `Environment`（读配置）→ 创建 `ApplicationContext` → `refresh()`（扫描 Bean、执行自动配置、初始化）→ 启动内嵌 Tomcat。
- **结合本项目**：启动时会执行 `spring.sql.init` 的 `db/schema-mysql.sql` 建 14 张表，然后装安全过滤链，最后监听 `127.0.0.1:8002`。

**Q5.3 配置加载优先级？怎么管多环境？**
- **简洁版**：命令行参数 > 系统/环境变量 > `application-{profile}.yml` > `application.yml`。可用 `spring.config.import`、`@ConfigurationProperties` 绑定。
- **结合本项目**：`application.yml` 用 `${ENV:默认值}` 让环境变量可覆盖；敏感凭据放 `application-local.yml`，用 `spring.config.import: optional:classpath:application-local.yml` 导入（**文件不存在也不报错**，别人 clone 下来能直接跑）；配置在 Java 侧绑定到 `config/AppProperties`（`@ConfigurationProperties("app")`）。
- **✅加分**：能说"配置集中一处 + 类型安全绑定，比到处 `@Value` 好维护"。

**Q5.4 Actuator 用过吗？**
- **简洁版**：`spring-boot-starter-actuator` 提供 `/actuator/health`、`/metrics`、`/env` 等运维端点。
- **结合本项目**：本项目**没有**引入 Actuator，而是自己写了 `HealthController` 返回 `{"status":"ok","version":...}`。答辩可答："我了解 Actuator，但这里为了保持前后端接口契约一致，用了自研的健康接口。"

## 模块 6 MyBatis / JPA

**Q6.1 MyBatis 和 JPA 区别？你项目用哪个？**
- **简洁版**：MyBatis 是"半自动"——SQL 你自己写，映射你控；JPA/Hibernate 是"全自动 ORM"——面向对象操作，SQL 自动生成。MyBatis 灵活可控，JPA 开发快、可移植。
- **结合本项目**：用 **Spring Data JPA**（ORM 层）。仓储**只声明接口**，方法名即查询（`findByIdAndUserId`）；复杂查询用 `@Query`（如跨会话搜索的 LIKE 与 JOIN 一次取回，避免 N+1）。
- **✅加分**：能说"JPA 的坑是 N+1 与懒加载，我用 JOIN/`@EntityGraph` 或直接 `@Query` 规避"。

**Q6.2 缓存 / 分页 / 懒加载？**
- **简洁版**：MyBatis 有一级缓存（SqlSession 级）、二级缓存（Mapper 级，需手动开）。JPA 有**一级缓存（持久化上下文）** 和二级缓存（需配）。分页：JPA 用 `Pageable`，MyBatis 用 `PageHelper`。懒加载：`LAZY` 关联对象首次访问才查库（**脱离事务会抛 LazyInitializationException**）。
- **结合本项目**：关掉了 **OSIV**（`open-in-view=false`），避免数据库连接被整个 HTTP 请求占用——所有查询都在 Service 的事务边界内完成。
- **✅加分**：能解释"关 OSIV 是主动选择，逼自己在事务内取完数据，避免连接泄漏"。

## 模块 7 MySQL

**Q7.1 为什么用 B+ 树做索引？聚簇 vs 非聚簇？**
- **简洁版**：B+ 树**层高低（磁盘 IO 少）、叶子节点有序且相连（范围查询快）**、非叶子只存键（可容纳更多）。InnoDB 主键索引是**聚簇索引**（叶子存整行数据），二级索引叶子存**主键值**，需**回表**；用覆盖索引可避免回表。
- **追问**：最左前缀原则？→ 联合索引 `(a,b,c)` 只能从 a 开始连续匹配。
- **结合本项目**：14 张表都建了主键与常用查询索引（如按 `user_id` 查）；`files/kb_chunks` 用外键字段关联。答辩可答"我按最左前缀设计了 `(user_id, created_at)` 之类索引"。
- **✅加分**：能说"索引不是越多越好——占空间、拖慢写入"。

**Q7.2 事务 ACID / 隔离级别 / MVCC？**
- **简洁版**：ACID = 原子性/一致性/隔离性/持久性。隔离级别：读未提交、读已提交（RC）、**可重复读（RR，MySQL 默认）**、串行化。RR 靠 **MVCC**（undo log + ReadView 快照）解决不可重复读，用**间隙锁（Next-Key Lock）** 解决幻读。
- **结合本项目**：表引擎 InnoDB；时间列用 `DATETIME(6)` 保微秒；JDBC 用 `connectionTimeZone=LOCAL&preserveInstants=false` 解决"存/查差 8 小时"。
- **✅加分**：能讲清"RR 下 MVCC 读的是快照，所以同一事务两次读结果一致"。

**Q7.3 锁 / explain / 慢查询 / 分库分表？**
- **简洁版**：行锁、表锁、间隙锁、意向锁；`EXPLAIN` 看 `type`（至少 range，最好 ref/const）、`key`、`rows`、`Extra`（避免 `Using filesort`/`Using temporary`）；慢查询开 `slow_query_log` + `long_query_time`；数据量大再谈分库分表（垂直/水平、ShardingSphere）。
- **结合本项目**：数据量不大（个人助理），**不需要分库分表**；但规避了 N+1（用 JOIN 一次查）、给检索字段加了索引。
- **⚠️避坑**：别一上来就说分库分表——面试官想听"先优化 SQL/索引，量级到了才分"。

## 模块 8 Redis（本项目未使用，可这样答）

**Q8.1 数据类型 / 持久化 / 过期策略？**
- **简洁版**：String/Hash/List/Set/ZSet（+Bitmap/HyperLogLog/Stream）。持久化 RDB（快照，恢复快、可能丢数据）/AOF（追加日志，更安全、文件大）。过期策略：**惰性删除 + 定期删除**；内存满按 `maxmemory-policy`（如 `allkeys-lru`）淘汰。
- **结合本项目**：本项目**没有引入 Redis**——个人助理是单机、并发低，缓存直接用**进程内**结构即可（如 `AgentCache` 用 `ConcurrentHashMap` 缓存构建好的 Agent、`RagSourcesBus` 用 `ConcurrentHashMap` 收集来源、日历用**磁盘文件缓存 7 天 TTL**）。答辩可答："规模不需要 Redis；若要多实例部署，会把会话/缓存外移到 Redis。"（这样答**既诚实又体现技术判断**）

**Q8.2 缓存穿透 / 击穿 / 雪崩 / 分布式锁？**
- **简洁版**：穿透=查不存在的数据（布隆过滤器/缓存空值）；击穿=热点 key 过期瞬间打爆（互斥重建/逻辑过期）；雪崩=大量 key 同时过期（过期时间加随机）。分布式锁：`SET key value NX PX` + Lua 释放，或 Redisson（看门狗续期）。
- **结合本项目**：日历缓存用**文件 + 7 天 TTL**，属于"避免频繁联网"的缓存；`AgentCache` 是"避免重复构建 Agent"的缓存——这两处都能拿去类比"缓存是为了省昂贵操作"。

## 模块 9 消息队列（本项目未使用，可这样答）

**Q9.1 MQ 的作用？Kafka/RabbitMQ/RocketMQ 区别？**
- **简洁版**：解耦、异步、**削峰填谷**。Kafka 吞吐最高（日志/流、分区顺序）；RabbitMQ 路由灵活（Exchange/Queue、事务/确认）；RocketMQ 阿里系（事务消息、延时消息、顺序消息）。
- **结合本项目**：本项目**没用 MQ**。可答："当前场景（单用户请求-响应 + 流式对话）不需要 MQ；如果要做**批量离线索引**（把上传文档的后台向量化做成异步任务），我会引入 MQ 做削峰。"——把"没用"转化成"我知道什么时候该用"。

**Q9.2 顺序消息 / 幂等？**
- **简洁版**：顺序=同 key 进同分区/队列；幂等=消费端用唯一 ID + 去重表/Redis SetNX，保证重复消费不产生副作用。
- **结合本项目**：类比——`indexFile` 是**幂等**的（先 `deleteByUserIdAndFileId` 清旧片段再写新），重复索引不产生重复数据。这个例子很适合说明"幂等设计"。

## 模块 10 计算机网络

**Q10.1 HTTP/HTTPS、TCP 三次握手四次挥手？**
- **简洁版**：HTTP 明文、HTTPS = HTTP + TLS（非对称握手协商出对称密钥）。三次握手（SYN→SYN+ACK→ACK）确认双方收发能力；四次挥手（FIN→ACK→FIN→ACK）因 TCP 全双工，需各自关闭。
- **追问**：TimeWait 为什么 2MSL？→ 保证最后的 ACK 到达、旧连接报文消散。
- **结合本项目**：后端监听 `127.0.0.1:8002`；前端开发时经 Vite 代理访问（同源）。**必答题**：Windows 下 `localhost` 可能解析到 IPv6 `::1`，而后端只绑 IPv4 `127.0.0.1`，所以代理/绑定都要写 `127.0.0.1`（真实踩过的坑）。

**Q10.2 WebSocket vs SSE？本项目用哪个？**
- **简洁版**：WebSocket 全双工（要协议升级）、SSE 单向（服务器→客户端，基于普通 HTTP，天然支持断线重连、文本友好）。聊天"边生成边显示"用 **SSE 足够**。
- **结合本项目**：对话用 **SSE**（`SseEmitter`），定义了 5 类事件：`token`（正文增量）、`reasoning`（思考增量）、`sources`（知识库来源）、`done`（结束）、`error`（错误）。断连/超时会回写部分内容并清记忆。
- **✅加分**：能说"选 SSE 是因为只需服务器单向推、且实现比 WebSocket 简单、能复用 HTTP 鉴权与代理"。

## 模块 11 操作系统

**Q11.1 进程 vs 线程 vs 协程？**
- **简洁版**：进程是资源分配单位（独立地址空间），线程是调度单位（共享进程资源），协程是用户态轻量线程（如 Go/虚拟线程，切换不开销）。
- **结合本项目**：Java 21 支持**虚拟线程**（`Thread.ofVirtual()`），对"大量阻塞 IO（等模型响应）"场景能显著提升吞吐；这是可以在答辩里说的"未来优化点"。

**Q11.2 IO 模型 / 零拷贝？**
- **简洁版**：五种 IO 模型——阻塞、非阻塞、**IO 多路复用（select/poll/epoll）**、信号驱动、异步。零拷贝：`mmap`、`sendfile`（DMA 直接在内存间搬，减少用户态/内核态拷贝）。
- **结合本项目**：文件上传走 `MultipartFile`（Tomcat 落盘/内存），下载/预览走 `Files` 读写；大文件场景可提"零拷贝/`transferTo`"。

## 模块 13 分布式与微服务（本项目未使用，可这样答）

**Q13.1 CAP、注册中心、配置中心、网关、限流熔断、分布式事务？**
- **简洁版**：CAP = 一致性/可用性/分区容错，三者不可兼得（P 必选，C 与 A 取舍），实际多为 **AP + 最终一致**或 **CP**。注册中心（Nacos/Eureka）、配置中心（Nacos/Apollo）、网关（Gateway）、限流熔断（Sentinel/Resilience4j）、分布式事务（2PC/TCC/Saga/本地消息表）。
- **结合本项目**：本项目是**单体应用**（Spring Boot 单进程），刻意**不引入微服务**——个人助理的规模用单体更简单、更好维护。答辩可答："我了解微服务体系；但我选择单体 + 清晰分层，因为**过早微服务会带来分布式事务、链路追踪、部署复杂度**，这些对当前需求是负收益。"（**这个答法非常加分**：体现"不以用新技术为荣，以解决问题为本"）

**Q13.2 你的系统怎么保证可扩展？**
- **结合本项目**：多模型接入本身就是一个**可扩展点**——新增一个 OpenAI 兼容平台只需在 `llm_providers` 表加一行（base_url + key + model），`ChatModelFactory` 无需改动（符合**开闭原则**）。这也是很好的"面向接口编程"案例。

## 模块 14 项目实战（答辩重点，必背）

**Q14.1 项目最大的难点是什么？**
- **参考答法**（选 1~2 个讲透）：
  1. **多模型动态路由**：模型不是启动时定死的，而是**按会话**从数据库读凭据动态构造（`ChatModelFactory`），且 Agent 构建昂贵 → 设计了 **8 维复合缓存键**（会话/供应商/模型/技能集/知识库集/思考开关/预算/接入 id）。踩过的坑：**键里 id 集合必须排序**，否则"配置没变却反复重建 Agent"。
  2. **契约兼容**：后端要与前端约定的 API **逐字一致**（JSON snake_case、错误体 `{"detail":...}`、5 类 SSE 事件），这样前端**零改动**。
  3. **上下文压缩**：长对话会撑爆窗口 → 保留最近 N 条 + 更早压成摘要（`SummarizationHook`）。

**Q14.2 多模型路由怎么做的？**
- **简洁版**：`provider=ollama` 走本地、`cloud` 走 OpenAI 兼容；`ChatModelFactory` 工厂分流；`ModelCatalog` 判定模型能力（上下文窗口、是否支持思考）。**关键点**：本地走 **Ollama 原生接口**（只有原生接口的 `think=false` 才生效，能关掉 qwen3 的思考提速 3~5 倍）；`enable_thinking` 只对**百炼域名**透传（别的平台传未知参数有被拒风险）。
- **✅加分**：能讲"为什么不用 starter 自动配置"（见 5.1）。

**Q14.3 API 隔离 / 多租户怎么做？**
- **简洁版**：靠 **JWT** 认证 + **仓储层强制带 `userId`** 过滤。
- **结合本项目**：每个请求经 `JwtAuthenticationFilter` 解析出当前用户 → 控制器用 `@AuthenticationPrincipal AuthUser me` 取到 → 服务层私有方法 `requireOwned(userId, id)` 查 `findByIdAndUserId`，**取不到抛 404 而不是 403**（**不泄露资源是否存在**）。这是很专业的安全细节。

**Q14.4 缓存设计？**
- **结合本项目**：三类缓存——① `AgentCache`（省"构建 Agent"的昂贵开销）；② 日历**磁盘缓存 7 天 TTL**（省联网拉节假日）；③ `RagSourcesBus`（本轮请求内收集来源，会话结束即清）。共同点：**都是为省"昂贵操作"**，且都有清理策略避免内存泄漏。

**Q14.5 前后端交互 / 性能优化？**
- **结合本项目**：① 开发用 Vite 代理解决跨域；② 聊天用 **SSE 流式**提升"首字响应"体感；③ 检索用 `max-total-chunks=30` 限制送模型的片段数，控制 token；④ Agent 缓存避免重复构建；⑤ 关 OSIV 避免连接被长期占用；⑥ 索引 + 避免 N+1。
- **✅加分**：性能优化要**先量化再优化**（能说出"首字延迟"和"token 成本"这两个指标就很专业）。

## 附录 B：答辩通用技巧
- **先给结论再展开**："这是 XX 问题，原因是 YY，我用 ZZ 解决，验证结果 WW。"
- **主动说踩坑**：面试官最喜欢"我发现……通过……定位到……最后……"的排查故事（本项目 `docs/优化记录.md` 全是现成的）。
- **承认不知道**："这块我没深入，但我知道可以从 A/B 入手，回去我补一下。"比硬编强。
- **不要说**：项目里"用了 Redis/微服务/分库分表"（本项目确实没用）；也不要贬低单体或说"技术越新越好"。
